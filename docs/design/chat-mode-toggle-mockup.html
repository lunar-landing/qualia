对标分析

Claude Code（官方文档 + plan mode 内部实现逆向）与 OpenAI Codex（官方仓库）
Claude Code · Plan ModeCodex · Read-Only Sandboxqualia · 本方案

写工具可见性 可见，靠提示词约束（"it is just prompt reinforcement"） 可见，越界由沙箱拒绝 不可见（从工具列表移除，零幻觉调用）
模式作用域 会话级（CLI 进程持有，Shift+Tab 切换） 会话级（/approvals 切换） 消息级（每条消息携带，localStorage 记偏好）
正交维度 permission rules 叠加 approval policy 叠加 disabledTools 配置叠加，一致
闭环 UX 计划 → 批准 → 自动切执行 — 二期预留（见 03 标注）

不学工具可见靠约束

Claude Code 保留写工具是因为有权限闸门兜底；我们没有该基建，可见会引发「尝试→失败→重试」循环。直接移除：零幻觉、省 token。

不学OS 沙箱硬隔离

Codex 方案最彻底但成本与场景不成比例；吸收其「维度正交」分层思想即可，模式与 disabledTools 互不侵犯。

坚持消息级参数

两家是单会话 CLI，进程持有状态无并发问题；我们是 Web 多会话 + ChatService 单实例，消息级是唯一不互相污染的做法。

06

设计决策（定稿）

D1请求级参数，非 Agent 实例状态

ChatService 单实例多会话并行，实例字段会互相污染（detectedLanguage 同款教训）；模式随消息走，天然隔离。

D2工具移除，而非「可见靠约束」

对标结论：Claude Code 依赖权限闸门兜底才敢让工具可见；我们无此基建，从列表移除是最硬的等价实现，且省轮次与 token。

D3instanceof 黑名单 + 执行兜底

写 / 执行类集中一个方法维护，不改 FunctionTool 接口；执行层兜底防模型幻觉调用，反馈后自行纠正。

D4模式不入会话存储

前端 localStorage 记偏好、每条消息携带；与 disabledTools 配置正交叠加，历史回读与存储结构零改动。

D5命名「问答」而非 plan mode

定位是只读问答，不承载「计划→批准→执行」工作流；语义诚实，不给一期背工作流复杂度。

D6闭环 UX 二期落地

借鉴 Claude Code「批准→执行」流：只读回答卡片加「切换到智能体模式执行」按钮；一期由提示词文案引导衔接。
