执行步骤流输出重设计

思考流式输出到步骤区 · 回答区执行期间保持干净

SSE 事件链路调整

协议增量

核心变更：content 增量不再透传为 answer 事件（废除「闪现回答区再撤回」），改为新增 thinking 事件—— 每轮意图思考以累积全量推给前端，步骤区的思考行实时打字；THOUGHT step 事件照常在工具调用确认后到达（定格思考行）； answer 事件只在最终回答时发出。回答区在整个执行期间为空，直到最终回答落位。

事件载荷触发时机前端去向
thinking thought：本轮意图累积全量 流中每个 content 增量到达时 步骤区「当前轮思考行」替换渲染（打字机）
step · THOUGHT 完整步骤（不变） 流结束且确认 tool_calls 非空 思考行定格（去 spinner），随后 ACTION 步骤入列
step · ACTION / OBSERVATION 完整步骤（不变） 工具执行前后（不变） 工具行 / 结果（不变）
answer 最终回答全量 流结束且无 tool_calls（本轮 content 即回答） 回答气泡落位（方案一）或回答轮二次流式（方案二）
answer 透传 + 空 answer 撤回 — — 废除：意图不再经过回答区

场景二 · 直接回答（无工具）与回答落位策略

关键取舍

流式协议下「本轮 content 是意图还是最终回答」要等流结束才能确认，因此两种方案都让文本先在思考行打完，差别在最终回答的呈现方式。

方案一 落位（推荐） 单循环 · 零额外调用
qualia 的会话记忆存在哪
会话记忆持久化在 ~/.qualia/code/sessions/ 下…
流结束 · 无 tool_calls → 思考行淡出，全文落位回答气泡
会话记忆持久化在 ~/.qualia/code/sessions/ 下，按会话 ID 分目录存储，包含消息与 ReAct 步骤，重启后随会话回显恢复。
方案二 回答轮二次流式 多一次 LLM 调用
qualia 的会话记忆存在哪
（判定轮：无工具调用，content 丢弃不展示）
进入回答轮重调 LLM → answer 增量流式
会话记忆持久化在 ~/.qualia/code/sessions/ 下▍（真打字机，逐字出现）

策略对比与落地映射

维度方案一 · 落位方案二 · 回答轮二次流式
回答区污染均彻底解决：意图思考只流经步骤区，回答区直到最终回答才出现内容
最终回答呈现思考行打完后瞬时落位（无二次打字）回答轮重新生成，回答区真打字机
调用成本零额外调用（content 即回答）每次回答多一次 LLM 调用（判定轮作废）
回答质量与思考行文本完全一致回答轮可携带「回答风格」约束，可微调措辞
改动面后端：answer 透传/撤回逻辑 → thinking 事件；前端：思考行组件 + 落位后端：thinking 事件 + 恢复回答轮（buildFinalAnswerMessages 回归）；前端同左
推荐 方案一（落位）：直接回答是最高频场景，为它多付一次调用且内容重复生成不划算；思考行用次要色、回答气泡用主色，落位即视觉层级转换，配合 150ms 淡入足够自然。若实测觉得「直接回答必须二次打字机」，再升级方案二（协议兼容，仅后端加回回答轮）。
